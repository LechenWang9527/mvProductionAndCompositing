# 用 DeepSeek 做出「精致」的歌词 MV：从 `ref_mv` 拆出来的方法

> 目标读者：一个人，一首歌，手上只有 DeepSeek（它只出代码和文本，出不了画面，也听不到声音）。
> 参考样本：`ref_mv/`（Mili《world.execute(me);》歌词 MV 第四版开源工程，B 站 BV186pc65E68）。
> 本文引用路径一律相对仓库根目录 `E:\新建文件夹\实习\MV`；`ref_mv/…:行号` 指该文件的行。

## 0. 结论先行

这支 MV 的「精致」不是画得好，而是**每一帧都能被算出来、被单独重渲、被机器判对错**。三件事决定了它和业余作品的差距：

1. **画面是时间的函数，不是剪辑的产物。** 全片唯一入口是 `ref_mv/src/engine/engine.js:142` 的 `renderFrame(t)`，预览和 4K 导出走同一条路。没有跨帧状态、没有墙钟、没有 `Math.random()`。于是任何一帧可以随时重渲，任何改动可以逐像素比对。
2. **观感被翻译成了可测的数字。** 闪烁最差一秒 2.0 次（门槛 3）、红色闪烁 0、音频相对原 wav **+0.00 ms**、三个提示点 +17/0/0 ms、192.34 秒前最后一帧是全片最亮（luma 0.599）——这些数字来自 `ref_mv/tools/check_flash.py`、`check_sync.py`、`luma.py`，不是感觉。
3. **「改一处、坏一片」被工程手段堵住了。** `base_sheets` / `regress_sheets` / `compare_sheets.py` 让「没打算改的地方一格都不差」变成可执行的一条命令。第四版改了 `art.js`、`ascii.js`、`type.js`、`kit.js` 这类被所有段落共用的文件，重做过的 298 格**零差异**（`ref_mv/docs/v4/PROGRESS.md:73-76`）。

对只有 DeepSeek 的人，含义很直接：**你要做的不是「让 AI 帮你画」，而是「把 MV 写成一份可验收的规格，让 AI 实现、让脚本判分、你只在必须动眼睛和耳朵的地方出现」**。本文第 6 节给可直接粘贴的提示词，第 7 节给 12 步流程与人力分配，第 8 节给 32 条可勾选清单。

## 1. 核心结构：为什么「每帧只由 t 决定」是精致的前提

### 1.1 它是怎么组织的

```
config.json ──► createEngine()                 ref_mv/src/engine/engine.js:58
                  ├─ loadFonts()    第一帧前全部字体加载完（缺字直接抛错）   :19
                  ├─ loadArt()      剪影分墨版、描路径只做一次
                  ├─ buildScenes()  src/scenes/index.js → 镜头清单
                  └─ renderFrame(t) 唯一的每帧入口                     :142
                        ├─ layerA  出镜镜头（正在离开的）
                        ├─ layerB  入镜镜头（只在两镜时间重叠时存在）
                        └─ over    HUD / 片头警告页 / 片尾注记（不参与转场）
                              ↓
                        Post.render()  WebGL2 三个 pass            ref_mv/src/engine/post.js:1-14
                              mix（A+B 转场 + HUD）→ bloom（5 级模糊金字塔）→ final（相机/花屏/扫描线/暗角/颗粒/闪光）
```

- `renderFrame(t)` 里的 `t` 是**歌曲时间**（音频开始 = 0），不是成片时间。
- 真正的「一帧」由三张 canvas 和一个后处理链合成，所以转场不是预渲染素材，而是两镜重叠区间里的混合（见第 4 节）。
- `defaultFx()`（`engine.js:85-104`）每帧从零构造一次后处理参数：`flash/glow/zoom/rot/aberration/glitch/mosh/mosaic/invert/desat/scan/vignette/bright/hud`。**没有一份参数被上一帧继承**——这是"纯函数"在实现层面的样子。

### 1.2 三条禁令，和它们各自换来的东西

| 禁令 | 实现位置 | 换来了什么 |
| --- | --- | --- |
| 不读墙钟 | 只有导出进度条用 `Date.now()`（`ref_mv/export/export.mjs:134`，注释写明「只用于进度显示」） | 同一 `t` 在任何机器上渲出同一帧，缩图比对才有意义 |
| 不存跨帧状态 | `layer.begin(tv, f, t, fx)` 每帧重置；渲染时不 `getImageData`（像素只在加载时读一次） | 可以只重渲一段、只重渲一格，不必从头跑 |
| 随机来自种子 | `prng.js` 的 `rand(键, 帧号)`；`engine.js:59` 的 `setSeed(cfg.seed)`（`config.json → seed: 20161011`） | 颗粒、抖动、粒子都是「可复现的随机」；回归比对不会被噪点搞出假差异 |

连「抖动」也得确定性：`shot.js:67-71` 的 `shake(t, amp, seed)` 用几组正弦叠加，不用随机数；`type.js` 的 `limp` 用分条位移做下垂，不读像素。

### 1.3 代价：这套结构逼你做的事

- **加载必须前移。** 字体在 `loadFonts()`（`engine.js:19-46`）里 `FontFace.load()` 全部 await；CJK 字体按 `config.json → fonts.cjk[].text` 列出的字逐字校验，`document.fonts.load()` 返回空就 `throw`——因为「悄悄退回系统字体」是画面上最难发现、最毁精致的一种错误。同理 `art.inks()` 在加载时分墨版、`f_eye`/`f_reach` 在加载时描矢量路径。
- **文字 API 要会报错。** `ctx.text` 碰到字体没有的字符必须报错。`ref_mv/docs/v4/KIT.md` 列了可用字符集（Latin-1、常用标点、`²³−×↑↓`），并明说没有 `→ ♥ ✓ ∞ π`、没有框线、没有 emoji——要就画成形状。
- **已知例外要写下来。** GPU 后处理同一时间点重渲可能差 1/255；144.34 秒（glitch 首帧）两次渲染约 0.2% 像素不同，第三版即如此。写进 README 而不是假装不存在，回归比对才有容差依据（`compare_sheets.py` 用 `--level 6 --pixels 12` 兜住它）。
- **一镜坏不能带全片。** `drawScene()`（`engine.js:107-120`）捕获镜头异常，只报一次，然后在画面上写一行 `shot "id" failed: …` 继续渲。因为「能跑完」是回归比对、分段导出、4K 重跑的前提。

### 1.4 反面清单（这样做就失去精度的来源）

- 用 `requestAnimationFrame` 累积状态做动画：粒子速度、上一帧坐标、缓动进度存在对象里 → 不能任意时刻跳帧，不能 A/B 比对。
- 用实时录屏替代逐帧导出 → 帧率不稳、掉帧不可复现、4K 无从谈起。
- 用 `Math.random()` 做颗粒/抖动 → 每次比对都有假差异，人开始不信比对结果，回归就废了。
- 把「时间」写死在镜头里（`at: 12.345`）→ 换歌、换 BPM、改 preroll 全崩。`ref_mv` 的做法见第 2 节。

## 2. 时间三层：音频 / 歌词 / 节拍网格，以及负时间

### 2.1 三层各是什么

| 层 | 数据 | 谁维护 | 提供什么 API |
| --- | --- | --- | --- |
| ① 音频特征 | `ref_mv/data/audio_features.json`（约 1.8 MB，`tools/analyze_audio.py` 生成） | 脚本，换音频才重算 | `Features`：`bpm`、`t0`、`period`、`barTime(n)`、`beatTime(b)`、`snapHalf(t)`、`snapToBeat(t, tol)`、`sample(t)`→`{lowEnv, highEnv, onsets}` |
| ② 歌词行 | `ref_mv/data/lyric_timing.json`（只有行时间，**不含文字**）→ 运行时由 `tools/fill_lyrics.mjs` 填成 `data/lyrics.json`（本机，不入库） | 人给词与顺序，脚本给时间 | `Lyrics`：`start(i)`、`end(i)`、`typed(i,t)`、`indexAt(t)`（`ref_mv/src/engine/lyrics.js`） |
| ③ 人工卡点 | `ref_mv/src/scenes/cues.js` 的 `CUES = { name: [秒, source, note] }` | 人耳 + 脚本实测 | `cue('name')` |

实测网格：**130 BPM，第 0 拍在 0.344 s，一拍 = 0.4615 s，第 n 小节 = 第 4n 拍**（`ref_mv/docs/v4/PLAN.md:128`）。

### 2.2 谁听谁的（这是最容易做错的一步）

- **剪点只用网格**：段落里写 `B(bar)` / `Bt(beat)`（可小数，133.5 = 反拍）/ `H(i)`（第 i 行起点吸附最近半拍）。`ref_mv/docs/v4/KIT.md` 的原话是「绝不写裸数字」。
- **镜内事件用 `cue`**：行内某个词、某个鼓点这类既不在网格也不是行首的时间，只出现在 `cues.js`，段落文件里 `cue('name')` 取。
- **歌词只移动它自己**：`config.json → timing` 三个旋钮各管一件事——`offset` 整体延后（负值提前）、`lyricOffset` 只移动歌词及跟随它的画面、`keywordSnap` 让全大写关键词行在距最近拍 ≤ 0.06 s 时吸附（`lyrics.js:12-13`，0 = 关）。
- **`cues.js` 每项必须标来源**：`measured`（脚本在音频里测到强起音）、`audit`（上一版量过）、`initial`（简报给的初值，还没验）、`analysis`（某轮人做的频段分析）。改时间只改这一个文件、只改数字，并把来源改成 `ear`。

这条纪律的实际价值：作者听不到声音（他在写代码，不在听混音），所以「我知道这里差半拍」必须变成「`cues.js` 里一个数」。第四版交付时 `cues.js` 里 56 项：实测 27、审计 15、初值 14（`ref_mv/docs/v4/PROGRESS.md:89`），最需要耳朵确认的十处单独列出——这就是把人的听觉做成了接口。

### 2.3 preroll 为什么在负时间

`config.json → safety.preroll = 5.0`。全片前面有一页无声的闪光警告（`ref_mv/src/scenes/overlay.js` 的 `prerollShot`），它占用**歌曲时间 −5 到 0**。

这个设计的三个后果，每一个都必须成立：

1. **拍点一个都不动。** 警告页不参与节拍网格，`B(0)` 仍然是 0.344 s。如果把它算进时间轴（即「第 0 帧 = −5 s，音乐从第 5 s 起」但镜头表按成片时间写），全片每个 `B(bar)` 都要 +5 s，歌词索引、`cues` 全部偏移，而且不可逆。
2. **成片时间 = 歌曲时间 + 5。** 面向观众的说法（警告范围 2:28–3:12）用成片时间，代码里一律歌曲时间。`tools/storyboard.mjs:95` 在分镜表里同时给出两种时间。
3. **检查脚本要能换算。** 导出时把第一帧的歌曲时间写进 mp4 的 `comment` 标签：`-metadata comment=mv_start=…`（`ref_mv/export/export.mjs:89`）。`check_flash.py`、`check_sync.py`、`luma.py` 都读它，这样所有报告都是歌曲时间，和 `cues.js` 对齐。

导出实现上还有两个细节值得抄：`--start` 默认取 `-safety.preroll`（`export.mjs:35`），音频用 `adelay=<采样数>S:all=1` 精确延迟（`:88`），并按采样数而非秒计算，避免累计误差。

### 2.4 换歌会动哪里（可移植性检查）

换一首歌，需要重做的只有：`tools/analyze_audio.py` → `data/audio_features.json`、`tools/parse_lrc.py` → `data/lyric_timing.json`、`cues.js` 全部重测、镜头清单的 `at` 全部重算。**不需要动的**：`renderFrame(t)`、`transitions.js`、`palette.js`、`art.js`、`post.js`、`tools/` 下全部检查脚本——因为它们只认 `t` 和网格。这就是「结构对了，内容随便换」的具体含义。

## 3. 视觉系统：把「风格」写成可判定的规则

业余 MV 的风格写在形容词里（高级、电影感、赛博），`ref_mv` 的风格写在**可判定的约束**里：一条规则要么能被脚本查，要么能被一眼判对错。四条支柱如下。

### 3.1 颜色 = 状态（不是配色）

`config.json → palettes` 里 9 个调色盘，每个是一**件事发生了**的状态，不是一种「风格」：`off`（灰阶：AI 未启动 / 对方离线）、`on`（炭黑界面 + 米白字 + 橙的我）、`warm`（同色相更暖更亮：对话升温）、`error`（红）、`errRed`、`errWarm`、`errCream`、`ash`（灰里留一点橙：人走了）、`dead`（熄灭）。

实现上：每个调色盘是 13 个**角色**（`ref_mv/src/engine/palette.js:9`）——`bg panel raised line text sub mute me meHot meDim err errDim bloom`——加两个标量 `glow`、`sat`。绘制代码永远只说角色名，不说颜色值：

```js
// ref_mv/src/engine/palette.js
export function mixPal(a, b, k)      // 两个状态线性混合（:48）
export function palTrack(keys)       // [[time, name, fade?], …] → t 的函数（:61）
```

于是「橙 = 我、米白 = 你、红 = 错误、灰 = 缺席」这组语义全片不用重复声明，换状态时自动成立。三条硬规则：

- **颜色只在发生了事的时候才变。** 全片第一个颜色是 15.11 s 火花图示亮起（`PLAN.md:46`），全片第一个红是 129.34 s（`:48`）。这两条是可以被脚本查的：在 129.34 s 之前，任何一帧都不允许出现 `err` 的玫瑰红。
- **要区分「状态」与「状态的一部分」。** 镜头声明 `palette: 'on'`，段内某个部件要变红时用 `ctx.setPal()` 局部改；引擎用 `ctx.statePal`（`shot.js:52-55`）保留「这个镜头处于什么状态」，供整帧的泛光色、背景色使用。少了这层区分，一个红色错误卡片会把整帧染红。
- **状态之间用混合，不用跳变**（除非剪点）。`palette: ['on','warm',k]` 或 `palette: (t,f,u)=>spec` + 另给 `state` 标签；版画沿用所在段的 spec，避免切点处颜色跳一下。

### 3.2 字体三分工

| 角色 | 字体 | 出现在 | 配置 |
| --- | --- | --- | --- |
| 系统与代码 | JetBrains Mono 300/400/700/800 | 开机日志、错误码、代码清单、终端、计时 | `config.json → fonts.mono` |
| AI 说的话 | Source Serif 4 400/600/700/900 + italic | 歌词（几乎全是它的消息）、大字版画 | `fonts.serif` |
| 界面与使用者 | Inter 400–800 | 聊天客户端、按钮、设置项、用户输入 | `fonts.sans` |
| 特例 | Noto Serif/Sans KR·TC | 数数卡、警告页中文 | `fonts.cjk[].text` 逐字列出 |

每个字体只用一种角色、只出现一次，是这支片子「看起来统一」的最大单一原因。落地时把它写成不可违反的规则（第 8 节 §C5）。

### 3.3 三墨版画与专色：把「有质感」拆成 5 个可判条件

「版画」在工程上是 `ref_mv/src/components/plate.js` + `ref_mv/src/engine/art.js` 的组合。判它是否过关，只用 5 条：

1. **第一帧就是干净、一眼认得出的整体轮廓**（不是靠动画慢慢成形）。
2. **大块平涂面**，不是线描小图标（把画面缩到 640 宽仍认得出——`PROGRESS.md:84` 就是这么验历史剪影带的）。
3. **只用三墨**：橙（`me`）、米白（`text`）、近黑（`bg`/近黑），加一支**专色**。
4. **明暗来自第二墨色或错开的阴影版**（`plate.shadow()`），不用渐变。
5. **纸底不是纯黑**：`plate.ground()` = 暖色近黑 + 两级平涂光斑 + 网点 + 颗粒 + 四角裁切标记。

专色的规则比三墨更死（`config.json → spot`）：只用在物件主体上、只在那一张版画里、随版画结束消失；`spot.eggplant #7B52AB`（另配 `light #A886D8`、`dark #452C68`）、`spot.tomato #D4432F`（`#EC6B4F`、`#8C2A1E`）。两条数值约束是给检查脚本用的：番茄的 `R/(R+G+B) < 0.7`（`check_flash.py` 把 ≥ 0.8 判为饱和红），且绝不品红（`err #f5506f` 是玫瑰红，会撞色）。**段落代码从 `cfg.spot` 取色，从不写 hex**。

### 3.4 剪影分墨版：一张图拆成三张版

`art.inks(ctx, name, dst, { roles, offset, reveal, exact, plates, keyline, crop, flip, alpha, vector })` 在加载时把一张 RGB 图按最接近的墨色分成橙/米白/黑三张蒙版，绘制时每张版各自映射到一个调色盘角色。这条设计一次解决了四件事：

- **身份即颜色**：她在 `off` 状态自动变灰，`error` 状态要显式指定灰/红角色——不需要为每个状态准备素材。
- **归属可让**：与用户米白界面同框时，她的米白版改印 `sub`，把真正的米白留给「你」。
- **可错版**：三张版各自有 `offset`（`10/18/28 px`），「腐坏」不重画素材。
- **可特写**：`vector: true` 时按描好的路径画，4K 下放大 3.5 倍不糊（其他图不超过 1.75 倍）。

配套三条硬规则（`ref_mv/docs/v4/PLAN.md:110-116`）：黑墨背后必垫纸底/光晕/描线（否则脸和外套融进背景）；被裁切的边必须与画面边或面板边重合；有脸的镜头只允许 cut / fade / 错版 / 降帧，不撕裂、不扭曲、不 RGB 分离。

### 3.5 抽象成「任何 MV 都能用」的 6 条设计约束

1. 一个符号只允许一种含义（橙 = 我，不能这支镜头里还代表警告）。
2. 一个变化只允许一个触发条件（颜色变 → 一定有事件；镜头切 → 一定在网格上；滤镜开 → 一定对应一个叙事动作）。
3. 一个字体只允许一种身份。
4. 一种材质只允许一套参数（版画永远三墨 + 1 专色；界面永远平涂 + 细线 + 柔和阴影；界面不加渐变）。
5. 一个母题贯穿全片（花形 = 火花 = 她的发饰 = 客户端图标，`ref_mv/src/components/motif.js` 的 `spark()`）。
6. 例外必须编号并写明失效时刻（专色只在主歌二两张版画、`f_eye` 第一次出现必须在 124.89 s）。没有编号的例外，过两天就会扩散成风格。

## 4. 镜头组织：shot → sequence → 重叠区转场

### 4.1 一个镜头就是一份数据结构

`ref_mv/src/scenes/shot.js:5-17` 定义了一个镜头的全部字段：

| 字段 | 必填 | 含义 | 谁校验 |
| --- | --- | --- | --- |
| `id` | 是 | 提意见、看图、报错都用它 | `storyboard.mjs` 表格 |
| `at` | 是 | 剪辑时间，只用 `B()`/`Bt()`/`H()` | 半拍网格检查 |
| `lines: [first,last]` | 视情况 | 本镜负责的歌词行（0 起） | 歌词覆盖检查 |
| `moment` | **是** | 「这是对话里的哪个时刻」 | 缺省即报错 |
| `layout` | 是 | 以 `interface:` / `PLATE:` / `CODE:` 开头 | 分镜表分类 |
| `palette` / `state` | 是 | 状态、混合、或 `(t,f,u)` 函数 | 129.34 s 前无红 |
| `enter` | 否 | 与前一镜的转场（`{type,dur,align,flash,…}`） | 时长是否塞得下 |
| `camera(t,f,u)` | 否 | `{x,y,zoom,rot}` | — |
| `render(ctx,t,f,u)` | 是 | 纯函数，`u = {at, until, dur, since, k}` | 重渲一致性 |

`sequence(defs, endTime)`（`shot.js:20`）做三件事：排序、算每个切点的重叠区、把定义变成引擎能渲染的场景。**转场不需要单独写**——它只是两镜时间重叠时的一段时间区间。

### 4.2 重叠区驱动转场，以及被钳制的那一步

```
enter: { type:'scan', dur:0.46, align:'end' }
   align 'end'    → 重叠区在切点之前（[dur, 0]）：推进、擦除「落在」拍上
   align 'start'  → 重叠区在切点之后（[0, dur]）：由拍点「触发」的花屏、碎裂
   align 'center' → 骑在切点上（[dur/2, dur/2]）
```

引擎只有两层内容层，所以**任意时刻最多两个镜头活着**。`shot.js:31-39` 因此对每个重叠区做双向钳制：前伸不得越过上一个切点、后拖不得长过它要进入的那个镜头，塞不下就 `console.warn` 并缩短。没有这层钳制，一个 0.9 s 的前伸会整个吃掉前一镜——这类 bug 在成片里表现为「某个镜头一闪而过」，肉眼极难定位，但日志里有一行。

重叠区的进度 `k` 同时驱动三样东西（`engine.js:155-165`）：

```js
k   = clamp((tv - B.start) / (A.end - B.start));
pal = mixPal(palA, palB, k);       // 颜色状态跟着转场混合
blendFx(fx, fxA, k);               // 后处理参数逐项混合（flash 取两者最大）
tr  = resolveTransition(B.enter, k, pal);   // 转场查表 + 用调色盘着色
```

`blendFx`（`engine.js:129-139`）里的 `of()` 逻辑值得抄：`mosaicRect`、`raysAt`、`zoomAt` 这类**坐标不能插值**（插值会让光心漂到画面中间），必须整取一方的值——这是「转场期间特效看起来不像糊了一层」的细节。

### 4.3 转场类型与选择动机

`ref_mv/src/engine/transitions.js:10-27` 是一张**带动机**的表，不是一个素材列表：

| 类型 | 形态 | 什么时候用（原文意图） |
| --- | --- | --- |
| `cut` / `cut+flash` | 硬切 / 带闪硬切 | 打击点、关键词落下 |
| `flashcut` | 藏在色光里的切 | 大的段落变化 |
| `fade` | 溶解 | 消失、失去、结尾 |
| `glitch` | 块 + 撕裂行互换 | 不稳定、错误 |
| `scan` | 带热边的扫描线（`dir` 0 下 1 上 2 右 3 左） | 「印刷」、开机 |
| `circle` | 从一点起的虹膜（`inverse` 关闭） | 聚焦到某物 / 从某物 |
| `diag` | 斜栅栏擦除 | 话题急转 |
| `grid` | 单元格对角级联翻转 | 数据、参数 |
| `zoom` | 穿画（`out` 反向） | 更深入 / 拉出 |
| `shatter` | 碎成下落碎片 | 破碎 |
| `dissolve` | 像素块随机翻转（`size` 块尺度） | 擦除、腐朽 |
| `winclose` / `winpop` | 像关窗/弹出窗 | 离开、关机 / 对话框、错误、新进程 |
| `push` | 双画面推（`dir`） | 两种状态互换 |
| `slices` | 横条撕开 | 撕裂 |

真正的规则是那句注释：**「keep it motivated by the lyric, not decorative」**。形状到形状的**匹配剪辑**不在转场库里做——在镜头里用 `shapes.js` 沿同一个轮廓跨硬切变形（例如 F→M 性别切换，`PLAN.md:148`）。

### 4.4 fallback：让「还没做」不等于「不能跑」

`ref_mv/src/scenes/index.js:45-60` 的 `buildShots()` 逐段 `import`，任何一段抛错就 `console.warn` 并继续；随后用 `fallbacks(env)`（`:33-42`）为**没有镜头覆盖的歌词行**补一个后备镜头（`kit.js` 的 `fallbackShot`：把歌词当 AI 的消息逐行打出），最后把片头警告页 push 进去。

这套机制的价值不是「防崩」，而是**让中间态可交付**：任何时刻导出都能得到一支完整的、能看的、歌词不缺的片子。但后备镜头会被告状——`storyboard.mjs:79` 把它列为四类问题之一，交付标准是「没有后备镜头」。**允许存在、必须被点名、不允许留在成片里。**

### 4.5 分镜表自动生成 + 四类自动校验

`ref_mv/tools/storyboard.mjs` 是整条流水线里最值得抄的一个脚本。它 `import` 段落模块（在 Node 里，`art` 用一个 `Proxy` 全部返回 `null`，`:25`），跑出真实镜头清单，然后：

1. **生成** `STORYBOARD.md`：段落总表（时间/镜头数/平均镜头长/颜色状态）+ 逐镜头表（时间、`小節:拍` 位置、`id`、歌词行、`moment`、`layout`、`state`、进入/离开转场）。表格从代码生成，**不可能与代码不一致**。
2. **校验四件事**（`:72-79`）：

```js
const missing  = 歌词行中没有被任何镜头 lines 覆盖的
const offGrid  = 切点不在半拍网格上（容差 2 ms，且 s.at > 0.3，因为警告页之前没有拍）
const noMoment = 没有 moment 或 moment 仍是 "not storyboarded"
const fallback = id 以 'todo-' 开头的
```

3. **把面向观众的闪光范围盖章进 README**（`:123-125`）：`<!-- flash-range -->` 标记之间由 `flashRangeText(cfg)` 计算写入，`成片时间 = 歌曲时间 + preroll`。**范围是算出来的，不是手打的**——这类「派生数据一律由脚本写」的习惯，是文档不腐烂的唯一办法。

一条经验：**把验收标准做成脚本的输出，而不是写在文档里让人去读。** 分镜表不是给人看的报表，是 CI 的断言。`package.json` 里它就挂在 `npm run storyboard`；第四版交付时的输出是「87 个镜头，歌词全覆盖，切点全在网格上，没有后备镜头」（`PROGRESS.md:41`）。

## 5. 工程化保证精致的手段：五件工具，每一件都对应一种「人眼看不出来但一定变丑」的退化

原则：**能被眼睛发现的问题交给人，能被脚本发现的问题一定交给脚本。** 下面每件工具都按「测什么 / 怎么读 / 为什么这能让观感变好 / 代价与边界」四段写，参数取自源码。

### 5.1 缩图回归：`base_sheets` + `regress_sheets` + `compare_sheets.py`

**测什么。** 把「改共用文件之前」和「之后」的画面各渲染成一批固定缩图（每拍或每半拍一格），逐格做像素比对，列出**哪些格变了、变了多少像素、最大差多少、变在画面哪个矩形**。

**怎么用（`ref_mv/tools/`）。**

```bash
# 改共用文件之前（art.js / draw.js / kit.js / type.js 这类被所有段落 import 的）
node tools/base_sheets.mjs s0        # → out/s0_{a1,a2,e,f}.png
node tools/regress_sheets.mjs r0     # → out/r0_{b,g,h1,h2,i}.png
# …改…
node tools/base_sheets.mjs s1
node tools/regress_sheets.mjs r1
python tools/compare_sheets.py --a s0 --b s1 --sets out/base_sets.json
python tools/compare_sheets.py --a r0 --b r1 --sets out/regress_sets.json
```

- `base_sheets.mjs` 的格点：`a1` = 第 0–63 拍、`a2` = 64–127（即 0:00–0:59）、`e` = 第 224–262 拍（103.73–121.73 s）、`f` = 271.5 + 272–319 拍（125.65–148.04 s）。这些是「v4 决定原样保留」的段落。
- `regress_sheets.mjs` 的格点：`b` 副歌一（59.42–74.19 s）、`g` 十二声+数数+最后一声（148.04–162.81 s）、`h1/h2` 最后副歌与 LOVE 四句（162.81–192.34 s）、`i` 结尾（192.34–211.5 s），**每半拍一格**（结尾每拍一格）。这些是 v4 重做过的段落。
- 两张表都是 `640×360`、`cols 8`、`pad 6`，通过 `export/export.mjs --sheet --times …` 出图，并把格点写进 `out/*_sets.json` 供比对脚本读。
- `compare_sheets.py` 的判据：`--level 6`（单通道差 > 6/255 才算「变了」）、`--pixels 12`（超过 12 个这样的像素才算「这一格变了」）。输出形如

```
[b] 64 tiles, 2 changed
    t=  61.980s    1834 px (  0.8 %)  max diff 118  box x 210-263 y 44-97   (of 640x360)
```

**为什么这能让观感变好。** 精致度最常见的损失不是「做错」，而是「顺手改坏」：调色盘里一个角色差 4 个色阶、角色的米白版换错角色、某个图形往左挪了 3 px、大字的字重从 700 变 800。这些在单帧里几乎看不出来，在全片里会变成「说不清哪里不统一」。人眼无法跨天比较两张缩图，脚本可以。第四版的实测：改完 `art.js`、`ascii.js`、`type.js`、`kit.js`、`05_chorus.js`，已重做的 B/G/H/I 段 **298 格零差异**；保留段落里所有差异都落在简报点名要改的时间窗内（`ref_mv/docs/v4/PROGRESS.md:73-76`）。这就是「可以放心重构」的前提——没有它，没人敢动共用文件，风格就会随段落分裂。

**代价与边界。** 必须允许容差：GPU 后处理同一时间点重渲可能差 1/255，所以阈值取 `level 6 / pixels 12` 而不是「任何像素不同即失败」；144.34 s 这一格本来就偶尔不同（glitch 首帧 ~0.2% 像素），要预先写进交付说明，否则每次比对都有一条假警报，久而久之就没人看了。

### 5.2 闪光安全：`check_flash.py`（WCAG 2.3.1 的近似量测）

**测什么。** 对导出好的 mp4，缩到 `64×36`，逐帧算两件事：

- **一般闪烁**：某像素相对它上一次极值完成一次 ≥ **10% 全幅**的亮度变化（且较暗的那一态亮度 < 0.80），并且这类变化覆盖 ≥ **25%** 画面。成对的反向变化算一次闪烁。
- **红色闪烁**：同一逻辑，但统计的是「进出饱和红」（判据 `R/(R+G+B) ≥ 0.8`）的转变，强度按红色分量加权。
- 判据：**任何 1 秒窗口内，任一种都不超过 3 次**。实现见 `flashes_per_second()`：对每像素在 1 秒窗内的转变计数，取「最忙的 25% 像素」所达到的值，再除以 2 得闪数（`ref_mv/tools/check_flash.py:55-62`）。
- 附带三项：硬切统计（相邻帧平均绝对差 > 0.12 的数量、最密一秒几处）、**单帧突跳**（`d1[i]>0.05 && d1[i+1]>0.05 && d2[i] < 0.35·min(d1[i],d1[i+1])`：第 i 帧与前后都不同、而前后两帧彼此相似 → 一帧误闪或丢帧）。
- 仓库里另有 `src/engine/ctx.flash()` 与 `safety.maxFlash = 0.7` 的运行时上限，但注释明确：**新光效（`fx.bloomAll`/`rays`/`streak`/`zoomBlur`）、`fx.bright`、反相都不受 `maxFlash` 限制，只有这个脚本能拦住**（`ref_mv/src/engine/post.js:8-14`）。

**怎么读。** 目标是**不只是 PASS**：第四版全片 13017 帧的结果是「一般闪烁最差一秒 **2.0**、红色 **0**、单帧突跳无」，最差处在 50.83 s（导歌一 Vision 开关连点），并且分段量测逐段留档（−5–18 s 1.0 / 47–53 s 2.0 / 58–76 s 1.0 / 103–149 s 1.0 / 146–197 s 2.1）。

**为什么这能让观感变好。** 两层：

1. **安全**：光敏性癫痫的行业门槛，也是平台与发布的要求。这条在「精致」之外，属于必须过的线。
2. **审美**：3 次/秒的预算**逼出了两种更好的做法**——「亮度靠持续不靠脉冲」（`ref_mv/docs/v4/PLAN.md:237`）和「光是棘轮」（`:198`，镜头内只升不降、只在切点下降）。结果是高潮段不是廉价频闪，而是一路推到全片最亮的一帧（192.20–192.33 s，luma **0.599**），再一刀落到 0.345。**限制不是精致的敌人，是精致的模具**：没有这条预算，最容易做的选择就是每拍闪一下。
3. 它把「穿过一片方块或条纹的 zoom」判为运动闪光（任何位置每秒被亮暗边界扫过 ≤ 3 次），于是这类镜头只能改成阶梯式推进——观感上从「晕」变成「有力」。

**代价与边界。** 它是 64×36 的近似，不替代专业 PSE 检测（`check_flash.py` 头注释原话）；必须先导出 60 fps 档再测，帧率不同统计会变。

### 5.3 音画同步：`check_sync.py`

**测什么。** 对成片做三个独立检验（`ref_mv/tools/check_sync.py`）：

1. **音频封装偏移**：把 mp4 解码出的单声道音频与原始 wav 在 ±2400 采样内做互相关（取前 30 s、去掉两端避免边界效应），得出「成片音频相对原 wav 提前/延后多少采样」。判据就是 0。
2. **画面提示点滞后**：取每帧 `64×36` 灰度均值，在三个已知「必定有亮度跳变」的提示点（开机首个瞬态 0.209 s、drop = `bar(8)`、enter = `bar(9)`）附近 ±6 帧内找亮度上升最大的那一帧，与期望帧比较，输出毫秒差。
3. **歌词 vs 人声起音**：对 wav 取谐波成分、STFT、**300–3400 Hz** 人声频段，做谱通量包络；把每行歌词起点相对包络在 ±0.40 s 内平移求最大响应，得整份 LRC 的系统性早晚；再逐行找 ±150 ms 内最近的起音峰，输出中位数与 IQR；最后统计全大写关键词行与节拍网格的偏差（中位数、落在 ±60 ms 内的比例）。

**为什么这能让观感变好。** 观众说不出「差 40 ms」，但一定觉得「不对口型 / 踩不准」。60 fps 下一帧是 16.7 ms；这台机器量到的是音频 **+0.00 ms**、提示点 **+17 / 0 / 0 ms**。第 3 项更关键：它把「LRC 整体偏早」这种系统性误差变成一个有符号的数（第四版已知 148–162 s 一段偏早，于是在那一段改用 `Bt()` 而不是 `H()`）。**观感上的「踩点准」= 时间轴上没有一个未量化的偏移。**

**代价与边界。** 只测「大事件落点」（因为靠亮度跳变），测不到细腻的表演；第 3 项只给统计量，具体某一行要人听——这正是它要输出「最需要耳朵确认的十处」的原因。

### 5.4 亮度曲线：`luma.py`

**测什么。** 对导出档逐帧（可 `--step 0.2308`，即每半拍）打印两个数：**gamma 编码的平均亮度**（`0.2126R+0.7152G+0.0722B`，人眼读到的「亮」）与**线性平均相对亮度**（`check_flash.py` 量的那个）。`--cuts` 给出切点列表后，它还会列出「同一镜头内亮度下降超过 `--tol 0.012`」的位置。`--tiles 4` 则用来量缩图表每格的亮度。

**为什么这能让观感变好。** 它守的是三个具体的主张：

- **「全片最亮的是最后一帧」**：一句话声明，必须能打印出时间点（192.20–192.33 s，0.599）。如果最强的爆点在中段，结尾就永远「顶不上去」，全片的力就泄了。
- **「光在镜头内只升不降」**（棘轮）：任何镜头内部的亮度回落都会被逐条列出。回落在新手作品里几乎是通病——每一段都想「加一点光再收回来」，全片就成了没有形状的呼吸。列为 0 条，观感上变成「一路推上去」。
- **安静处的亮度**：结尾那张版画被要求「静止 1.59 s / 完整画面 1.22 s」，这期间连引擎默认的「低频呼吸」（整幅随底鼓放大约 0.3%）都要关掉——同一件事需要**数值证明**（192.34 关灯之后到 193.27，除胶片颗粒外没有任何像素变化）。

**代价与边界。** 平均亮度会骗人：一张纯黑画面里一个小白点，和一张均匀中灰，均值可能相同。所以它配合缩图表看，不单独作为判据。

### 5.5 三个小工具（同样重要，容易被忽略）

| 工具 | 测什么 | 为什么 |
| --- | --- | --- |
| `tools/measure_cues.py` | 读 `cues.js` 每个条目，在音频里找它附近的强起音（人声频段 300–3400 Hz，强度 ≥ 0.75 才算），打印「你的值 / 实测值 / 差多少」 | 让人的耳朵变成可审计的输入；改时间只改一个文件 |
| `tools/check_no_lyrics.mjs`（`npm run check:lyrics`） | 入库文件里不得出现连续 ≥ 4 个歌词词，不得有音频/歌词档 | 版权与「词只从 `text(i)` 取」这条规则的技术兜底 |
| `tools/fill_lyrics.mjs` | 缺行时列出**行号 + 歌曲时间**并 `exit 1`，不渲染 | 宁可停，不出一支歌词错位的片子；预检在任何输出被触碰之前 |

### 5.6 这些手段合起来的形状

```
数据层     analyze_audio.py → audio_features.json        （网格）
           parse_lrc.py     → lyric_timing.json          （行时间）
           cues.js          ← measure_cues.py            （人耳可审计）
                ↓
实现层     renderFrame(t) 纯函数 + prng 种子 + 首帧前加载完成
                ↓
检查层     缩图  ── compare_sheets.py      （有没有改坏别人的画面）
           亮度  ── luma.py                （力有没有形状）
           闪光  ── check_flash.py         （安全 + 是否能承受"更亮"）
           同步  ── check_sync.py          （时间轴有没有未量化的偏移）
           结构  ── storyboard.mjs         （覆盖/对拍/moment/fallback）
                ↓
发布层     check_no_lyrics.mjs + README 里的量测数字（由脚本盖章）
```

**每一层都在回答一个「人眼答不了」的问题。** 这就是一个人（加上一个只会出代码的模型）能到 13017 帧精致度的真实机制：不是审美更好，而是把审美判断**一次性**做成规则和检查，然后让机器在每一次改动后重复执行它。

## 6. 给 DeepSeek 的提示词：结构 + 5 段可直接粘贴的模板

### 6.1 先说清楚 DeepSeek 的边界，提示词才知道该说什么

| 它能做 | 它做不到（必须由人或脚本代劳） |
| --- | --- |
| 写/改引擎、组件、镜头代码；读你的仓库自己定位 | 看画面（除了你贴截图/贴数字） |
| 读 JSON/日志/脚本输出，据此定位问题 | 听音频、判断踩点是否舒服 |
| 写检查脚本、跑分析结论、算网格时间 | 判断「这张版画是否一眼认得出」「这个笑点是否成立」 |
| 按规格生成镜头清单、`cues.js` 条目 | 决定叙事、取舍、风格方向 |
| 输出「我改了什么、预期数字是多少、请你跑哪条命令」 | 自己渲染（在你没有给它渲染环境时） |

**所以提示词的核心不是描述画面，而是：给它可验证的目标 + 让它输出可被你验证的证据。** 下面每段模板都遵守这个结构：

```
① 角色与权限（你是谁、能改哪些文件、不能改哪些）
② 目标与判定标准（做完之后，哪条命令的输出应当是什么样）
③ 硬约束（确定性、禁止项、命名规则、颜色/字体规则）
④ 输入数据（网格、歌词行、cues、现有文件清单）
⑤ 镜头清单格式（字段表 + 一条完整范例）
⑥ 验收与自检（要它自己跑/自己算的检查，以及交付时必须报告什么）
```

### 6.2 模板 T1：项目初始化（第一次对话用）

> 只跑一次。产出：可渲染的空片 + 三层数据管线 + 全部检查脚本。**目标是先把「能验收」造出来，再谈画面。**

```text
你是这个项目的技术负责人兼主要实现者。我要做的是一支歌词 MV：一首歌，全程由代码绘制，
逐帧渲染成 4K60 视频。我只会写文字和改配置，不会写代码；你写代码，我来渲染、看图、
报数字。请你按下面的要求从零搭出工程骨架。

【环境】
- Windows 11，Node 20+，本机装 Chrome 或 Edge，ffmpeg 用 ffmpeg-static 依赖（没有系统 ffmpeg）。
- 导出用 playwright-core + 无头 Chrome，把每帧原始 RGBA 通过管道直接喂给 ffmpeg，不落盘中间图片。
- 需要 Python 的分析脚本用 .venv（librosa / numpy / soundfile），只在重新分析音频与检查成片时需要。

【核心架构，必须照做，不要自创】
1. 只有一个渲染入口：`renderFrame(t)`，t 是歌曲时间（音频开始 = 0），预览和导出走同一条路。
2. `renderFrame(t)` 必须是纯函数：不读墙钟、不保留任何跨帧状态、不调用 Math.random()。
   所有"随机"来自 `prng.js` 的种子函数（种子写在 config.json），以 (种子, 整数键) 取数。
3. 字体、图片、JSON 在第一帧之前全部加载完成；渲染过程中不调用 getImageData、不做逐帧 canvas filter。
4. 三层 canvas：A（出镜镜头）、B（入镜镜头，仅在时间重叠时存在）、overlay（警告页/注记，不参与转场）。
   后处理用一个 WebGL2 pass 链：mix（A+B 转场 + overlay）→ bloom（5 级模糊金字塔）→ final
   （相机/花屏/马赛克/RGB 分离/去饱和/反相/扫描线/暗角/闪光/颗粒）。
5. 所有时间都是歌曲时间。片头有 preroll 秒的无声警告页，位于负时间（-preroll..0），不改变任何拍点；
   成片时间 = 歌曲时间 + preroll。导出时把第一帧的歌曲时间写进 mp4 的 comment 标签（mv_start=...）。

【必须同时交付的三层数据管线 + 五个检查脚本】
- tools/analyze_audio.py → data/audio_features.json：bpm、第 0 拍时间 t0、一拍 period、barTime/beatTime/
  snapHalf/snapToBeat、每帧 lowEnv/highEnv、onset 列表。
- tools/parse_lrc.py → data/lyric_timing.json：只有行时间，不含歌词文字；行内词时间如有则保留。
- src/scenes/cues.js：一个对象，每项 [秒, 来源, 说明]，来源只能是 measured / audit / initial / ear。
- tools/check_flash.py：对 mp4 缩到 64x36 逐像素统计，近似 WCAG 2.3.1 两项门槛
  （一般闪烁：≥10% 亮度往返且较暗态<0.80，覆盖≥25% 画面；红色闪烁：R/(R+G+B)≥0.8 的往返），
  判据是任何 1 秒窗口内不超过 3 次；同时报告硬切最密一秒、单帧突跳位置。
- tools/check_sync.py：① 成片音频 vs 原始 wav 的互相关偏移（ms）② 若干已知亮度提示点的帧滞后（ms）
  ③ LRC 行起点 vs 300–3400 Hz 人声起音包络的系统性早晚 + 逐行最近起音的中位数/IQR + 关键词行对拍偏差。
- tools/luma.py：逐帧打印 gamma 亮度与线性相对亮度，支持 --step/--from/--to/--cuts/--tiles；
  给了 --cuts 时列出"同一镜头内亮度下降超过 --tol（默认 0.012）"的位置。
- tools/base_sheets.mjs / tools/regress_sheets.mjs / tools/compare_sheets.py：按固定格点出缩图表，
  逐格比对（单通道差 > 6 且这样的像素 > 12 才算该格变了），列出变了的时间点与变化矩形。
- tools/storyboard.mjs：从代码里的镜头清单生成 STORYBOARD.md，并检查四件事：每行歌词都有镜头、
  每个剪辑点都在半拍网格上、每个镜头都写了 moment、没有 todo- 开头的后备镜头。

【硬约束（后续每次对话都有效）】
- 颜色用"状态"表达，不用色值：config.json → palettes 里每个状态是 13 个角色
  （bg panel raised line text sub mute me meHot meDim err errDim bloom）+ glow、sat 两个标量。
  绘制代码只说角色名，不写十六进制。
- 字体三分工且只用这三种：等宽=系统与代码；衬线=歌词与"我"说的话；无衬线=界面与使用者。
  字体文件用 OFL 授权，经 @fontsource 本地加载。CJK 字体在 config 里逐字列出用到的字，只预载这些。
- 文字绘制遇到字体没有的字符必须报错（不能悄悄退回系统字体）。
- 镜头里的时间只用 beat/bar 辅助函数（B()/Bt()/H()），绝不写裸数字；行内词/鼓点时间一律走 cues.js。

【验收】
1. `npm run preview` 能开一个页面，播放时显示当前镜头 id、颜色状态、这是叙事里的哪个位置，
   支持 ?t=秒、?w=宽&h=高、空格播放暂停、方向键跳秒、逗号句号逐帧；声音失败时不停机并写明原因。
2. `node export/export.mjs --sheet out/qa.png --times 1,2,3 --cols 3` 能出缩图表。
3. 空片导出 3 秒（含 preroll）成功，check_flash / check_sync / luma 三个脚本都能跑通并打印数字。
4. 报告你建了哪些文件、每条命令怎么跑、还有哪些占位（例如还没写任何镜头）。

不确定的地方自己定，不要停下来问我；做完把上面 4 条的实际输出贴给我。
```

### 6.3 模板 T2：写一段（最常用，一段一对话）

> 一段 = 一段歌词 = 一两个文件。**关键是镜头清单必须是表格 + 一条代码范例，而不是形容词。**

```text
这次只做一段：第 {N} 段，{起}–{止} 秒（歌曲时间），歌词第 {i}–{j} 行。

【先读，再动手】
- docs/PLAN.md 的「颜色=状态」与「质感标准」两节、docs/KIT.md 的镜头字段表与验收清单。
- 你要改的文件：src/scenes/{文件名}.js（新建）。共用组件能用就不改；
  要改共用文件（kit.js / draw.js / art.js / components/*）必须先说明改哪一行、为什么不能用现成函数。
- 我给的这一段的意图（叙事）、版画清单、每个关键词的时间，写在下面「本段设计」里。

【本段设计】
- 叙事：{这一段在讲什么，一句话}。
- 画面：{哪几张是界面镜头、哪几张是版画、哪几秒是纯代码}。
- 关键词与版画（一行一个）：
  | 关键词（第几行） | 出现时间 | 版画内容（一句可判标准） | 由什么结束 |
- 允许的转场：{只能从 transitions.js 的 cut / fade / flashcut 里选}。

【镜头清单格式（必须完全一致）】
每个镜头是一个对象，字段：
  id       kebab-case，唯一，后面我在批注里会用它点名
  at       剪辑时间，只能用 B(bar) / Bt(beat) / H(lineIndex)，可以带小数表示反拍
  lines    [first,last] 本镜负责的歌词行（0 起）；不能漏行，同一行不能只在一帧里出现
  moment   一句话：这是叙事的哪个时刻；版画则是"哪个词、由什么结束"
  layout   以 "interface:" / "PLATE:" / "CODE:" 开头
  palette  状态名（'on'/'warm'/'off'/'error'/'ash'/'dead'）或 ['a','b',k] 混合，或 (t,f,u)=>spec
           （函数要另给 state 标签）；段内版画沿用本段同一个 spec
  enter    与前一镜的转场 {type,dur,align,flash}
  camera   (t,f,u)=>({x,y,zoom,rot})，可省略
  render   (ctx,t,f,u)=>{…}；u={at,until,dur,since,k}

一个完整范例（照这个密度写，不要写伪代码）：
export function chorusShots(env) {
  const { T, H, B, Bt, P, text } = cues(env);      // 这些是共用工具，行时间/网格都从这里取
  return [
    {
      id: 'c1-sentence-1',
      at: B(32),
      lines: [32, 32],
      moment: 'The AI answers the question with one sentence.',
      layout: 'interface: thread, single message',
      palette: 'on',
      enter: { type: 'cut' },
      render(ctx, t, f, u) { … },
    },
    {
      id: 'c1-plate-bolt',
      at: H(33),
      lines: [33, 33],
      moment: 'The word BOLT: the spark strikes the dot. Ends when the user\'s cursor leaves.',
      layout: 'PLATE: bolt + dot, one caption band',
      palette: 'on',
      enter: { type: 'scan', dur: P, align: 'end' },
      render(ctx, t, f, u) { … },
    },
  ];
}

【硬约束（违反即返工）】
- render 是 t 的纯函数：不存跨帧变量、不用 Math.random()/Date、不在 render 外创建 canvas/pattern/path。
- import 段落文件与构建镜头清单时不能碰 DOM（storyboard 脚本会在 Node 里 import 它，那时 art 返回 null）。
- 歌词文字只能通过 text(i) 取，不许把歌词写进代码；画面上新增的任何文字是为此刻写的简短原创英文。
- 颜色只用角色名；本段例外只允许 config.json 的 spot 专色，且只在指定物件主体上。
- 镜头里没有"填充文字"：每个词要么是歌词，要么是为这一刻写的文案。

【验收（请在回复里逐条给出结论或数字）】
1. `node tools/storyboard.mjs`：本段覆盖的歌词行 = {i}–{j}，切点全在网格上，没有 todo- 镜头。
2. 每个 at 用 B()/Bt()/H() 的名字写出来（例如 at = B(32) = 59.42 s），我能对照拍点表核。
3. 列出本段所有非网格时间及其 cues.js 名字与来源（initial 的单独标出来，我要用耳朵确认）。
4. `--sheet` 出图点：每个切点后一帧、每个关键词落点、每个转场中点，给出建议的 --times 列表。
5. 说明你复用/新增了哪些共用函数；如果改了共用文件，列出文件名与行号。
不要停下来问我，按上面的设计直接做完。
```

### 6.4 模板 T3：看完图之后的修复轮（一次对话只改点名的东西）

> 这是第四版真实存在的一类提示词（`ref_mv/docs/v4/PROMPT_v4_fix.md` 就是它的范本）。它的精髓是：**给现象 + 给测量 + 给新时间表 + 给省钱的验证方式**。

```text
第 {N} 轮修复。全片已做完，绝大部分不变。这轮只改下面 {k} 件事，改完做一次针对性检查。
不要重构、不要整理旧文件、不要改没点名的段落。

【先读】
- 本文是这一轮的全部要求。
- docs/PROGRESS.md 不要通读（很长）：用搜索找状态表和工具用法。
- 需要时再查 KIT.md；镜头怎么写，看你要改的那几个文件本身就够了。
- 这个目录没有 git：动手之前把 src/ 和 config.json 备份到 backup/before_fix_{轮次}/。

【工作方式（照做，这是我给你的省时规则）】
- 只碰点名的文件：{文件列表}。
- 不另外探索方案，不派子代理，不开多代理流程。某个效果试两三次还不理想就简化它，
  在交付说明里写一句，继续往下做。
- 出图要省：只给改动过的镜头出缩图，每个镜头看三处——切点后第一帧、主事件那一帧、结束前一帧。
- 没改的段落用数值比对，不用眼睛看：跑 compare_sheets.py，只有报告有差异的格子才打开图看。
- 导出要省：检查片段各导一次；全片预览最后导一次；不过关时只重导有问题的那一段。
- 拍点不重新全测：只改本文点名的几个时间。

【问题 1：{一句话现象}】
- 现象（我看到/量到的）：{例如"性别那一句的第二个字母，画面落在鼓点 91.05 s，人声要到 91.72 s 才唱它，早半秒多"}。
- 测量：{给出可复现的测法与结果，例如取左右声道共有部分、持续成分、1100–2900 Hz 能量}。
- 把握程度：{哪些确定、哪些还有另一个候选值}。
- 规则：这一镜里人声是主事件，鼓点只留给预备动作和余震。
- 新的时间表（逐行给到秒 + 网格名）：
  | 时间 | 事件 | 类型（主事件/次要/预备动作） |

【问题 2：…】（同上结构）

【不该动的】
- {列出必须保持的：某些镜头的切点、某些颜色规则、某一帧的亮度地位}。
- 硬限制不变：任意一秒内大面积亮度往返不超过 3 次（以 check_flash.py 为准）；
  会回落的闪光最多每拍一次；半拍一次的连续事件只升不降；花屏图案保持 6 帧以上。

【检查与交付】
1. 动手前出一套比对底图（指定前缀），全部改完再出一套，逐格数值比对：
   除了 {点名的时间窗} 之外应当零差异；{已知例外} 那一格可以忽略。
2. 导出检查片段：{范围1}、{范围2}，后者跑 check_flash.py，通过再往下做。
3. storyboard 通过；全片预览只导一次，然后跑全片 check。
4. 更新 PROGRESS.md（追加一小节）与 README 里的检查数字。
5. 交付说明里写清楚：改了哪些文件；{关键时间}最终用的值及其 cues 名字；
   闪光最差一秒的数字与位置；哪里没有按本文做、原因是什么。
```

### 6.5 模板 T4：把「精致」变成可执行的自检（每段做完都跑）

> 不是让人读的清单，而是让 agent 逐条给结论的检查表。可以直接附在 T2/T3 末尾。

```text
做完之后，按下面 10 条逐条给出「过 / 不过 + 依据（数字或图名）」。不许写"已检查"了事。

1. 覆盖：本段每一行歌词，在被唱的整段时间内都可见可读吗？（给出每行的可见区间 [[起,止]]，
   和歌词行时间对比，确定没有"只出现一帧"或"下一句已开口还挂着上一句"）
2. 对拍：所有 at 都是 B()/Bt()/H() 吗？把每个 at 展开成秒，标出它落在第几小节第几拍。
3. 状态：本段 palette 的进入/退出是否由事件驱动？有没有在 129.34 s 之前出现红色（err 角色）？
4. 三墨：本段的版画是否只用三墨（+ 允许的专色）？明暗是否来自第二墨或阴影版（不是渐变）？
5. 首帧：每张版画切进来后的第一帧，是否已经是干净、一眼认得出的整体轮廓？
6. 文字：画面上每个词是歌词还是为此刻写的文案？有没有占位文字、有没有重复歌词？
7. 运动：是否有缓动/错峰/次级运动？有没有只靠透明度淡入的镜头？快动作是否有运动模糊或降帧处理？
8. 确定性：render 里是否出现 Math.random / Date / 跨帧变量 / 模块级可变对象？
   重复渲同一 t 两次是否一致（已知例外要说明）？
9. 性能与加载：是否有在 render 内创建 canvas/pattern/path？是否有 getImageData？
   字体与图片是否都在第一帧前完成？
10. 回归：本段是否碰了共用文件？碰了的话，给出 compare_sheets.py 的逐格结果，
    并说明差异是否全部落在本段的时间窗内。

最后给出两样东西：① 建议我跑的三条命令（出图 / 比对 / 检查），每条一行、可直接粘贴；
② 你认为这一镜里"最可能被我看出来但脚本查不到"的一处风险，并说明为什么。
```

### 6.6 模板 T5：换歌 / 换段落时重定时（可移植性）

```text
我要把整套工程换到另一首歌上。请按下面的顺序改，并且在每一步之后告诉我"哪些东西必须重算、
哪些可以不动"，不要一次性把全部文件重写。

【新的输入】
- 音频：{路径}；BPM 与第 0 拍时间由 analyze_audio.py 重新测（不要手填）。
- 歌词：{路径}.lrc；行数与顺序可能与原来不同。歌词文字不入库，运行时由 fill_lyrics 填出。
- 我希望保留的：镜头结构、颜色语义、字体分工、三件套检查脚本、全部组件。

【必须重算（脚本做）】
1. data/audio_features.json（网格 + 每帧包络 + onset）
2. data/lyric_timing.json（行时间）
3. cues.js 全部条目：逐条给 [秒, 'initial', 说明]，并在下一轮用 measure_cues.py 升级成 measured
4. 所有镜头的 at：把上一版按"第几小节第几拍"的语义重新映射到新网格，不要按秒平移

【不许动】
- renderFrame(t)、post.js、transitions.js、palette.js、prng.js、art.js 的接口
- 检查脚本的判据与阈值
- 颜色语义、字体分工、三墨/专色规则

【验收】
1. storyboard 通过（歌词全覆盖、切点全在网格、无 todo 镜头）
2. 空跑一遍全片导出，check_flash 与 check_sync 都能出数字（先不管好不好看）
3. 列出"新歌里我几乎肯定要用耳朵改的十处时间"，每条给行号 + 秒
4. 报告：动了几处代码、几处数据；哪一处是你判断"结构与歌曲绑定太紧、需要抽象"的，给出方案但先别改
```

### 6.7 七条话术要点（比模板本身更能决定成败）

1. **说「你听不到声音」「你看不到画面」。** 明确写出它的感知缺陷，它才会把时间写成 `cues.js` 的条目而不是猜。
2. **给它判定标准，不给形容词。** 「一帧里只有三个墨色」可判；「有版画感」不可判。
3. **禁止它停下来提问**（「细节由你决定，不要停下来问我」），但要求它**报告假设**。否则一次对话会卡在三个问题上。
4. **限定文件范围**（「只碰点名的文件」）。编码 agent 最大的破坏源是顺手重构共用文件。
5. **要求它输出可被你执行的命令**（出图 `--times` 列表、比对前缀、检查脚本调用），把渲染与观察留在你这边。
6. **要求它报告差异而不是宣称完成**（「哪里没有照本文做、原因是什么」）。这一条能救回一半的自欺。
7. **一次对话只推进一步。** 第四版是三次长对话做完全片（`ref_mv/docs/v4/PROGRESS.md:3`），每段一次交付 + 一次比对，这是「精致」在流程上的真实成本。

## 7. 从一首歌到成片：12 步，以及每一步谁来做

图例：**人** = 只有人能做的（听、看、判断、取舍）；**DS** = 可以整段交给 DeepSeek（给规格 + 收代码/脚本）；**脚本** = 机器判定，人只看数字。真实比例大约 **人 20% / DS 65% / 脚本 15%**，但那 20% 决定了剩下 80% 值不值钱。

### 第 0 步：备份与基准（DS + 脚本，30 分钟）

- **输入**：任何东西（甚至只是"我想做 MV"）。
- **动作**：建目录、建 `backup/v0/`、把将要被反复改的共用文件（调色盘、组件、引擎）先出**基准缩图**存成 `out/base_*.png`。装 Node/ffmpeg-static/playwright-core，跑通空片导出 3 秒。
- **产出**：`config.json`、能跑的空工程、基准图。
- **验收**：空片能导、三个检查脚本能出数（数字难看没关系）。
- **谁**：DS 写全部脚手架；**人只做一件事**：确认自己机器上 `npm run preview` 能开。

> 这一步最容易被跳过，而"没有基准"意味着后面每一次改动都无法判断是否改坏。**先造度量，再造画面。**

### 第 1 步：听歌并写下「哪几秒必须发生什么」（人，1–3 小时）

- **输入**：你的歌。
- **动作**：**戴耳机完整听 3 遍以上**，边听边记：段落边界、情绪顶点、哪一句歌词是"唱得很用力"的、哪一秒有一个必须踩中的鼓。**不要在这一步想画面**。
- **产出**：一张手写表：`时间（分钟:秒）| 发生了什么 | 强度 1–5`，大约 20–40 行。
- **验收**：表里至少有 **5 个"必须踩中"的时刻**，以及 1 个"全片最亮/最强"的时刻（它会成为结尾或高潮的基准）。
- **谁**：**只能是人的工作**，不能外包给模型。模型的输出（BPM、onset 列表）是数据，不是判断。

### 第 2 步：网格与歌词时间（DS + 脚本，1 小时）

- **输入**：`音頻&歌詞/你的歌.wav` + `.lrc`。
- **动作**：`tools/analyze_audio.py` 出 `data/audio_features.json`（BPM、`t0`、`period`）；`tools/parse_lrc.py` 出 `data/lyric_timing.json`（只有行时间）；跑 `lyrics:retime`；`fill_lyrics.mjs` 校验行数与顺序。
- **产出**：三层数据里的前两层。
- **验收**：`H(i)` 能打印每行起点；缺行时脚本报行号 + 秒并 `exit 1`；`Features` 的 `t0/period` 与第 1 步的表对得上（差 > 半拍就回去查 BPM 是否被双击/半速判错）。
- **谁**：全 DS。**人只做一次判断**：第一拍到底落在哪（听 10 秒前奏确认 `t0`）。

### 第 3 步：把第 1 步的表翻译成镜头清单（人 + DS，2–4 小时）

- **输入**：第 1 步的表、歌词行索引、网格。
- **动作**：写每段的**一页规格**：这一段是界面/版画/纯代码？有几句？关键词是哪几个词？每句的"视觉峰值"给哪一帧？——写成第 6.3 节 T2 里的那张表（关键词 / 时间 / 版画内容 / 由什么结束）。
- **产出**：`docs/SEGMENTS.md`（或每段一个 md），每段 ≤ 1 页，含镜头清单表。
- **验收**：每一行歌词在表里被某个镜头认领；每个镜头有 `moment`；每个版画有"由什么结束"。**空着的格子不许留到写代码时再想。**
- **谁**：**人定内容**（这是创作判断，`AGENTS.md` 明确说分镜/叙事/风格决策不下放）；DS 只负责把它排成合法字段、检查覆盖与对拍。

### 第 4 步：引擎与组件（DS，1–2 个对话）

- **输入**：T1 的架构要求、`ref_mv/src/engine/*` 作为参考实现（可让 DS 读）。
- **动作**：依次实现 `prng` → `features/lyrics` → `draw`（含 `ctx.text` 缺字报错）→ `palette` → `art.inks` → `post` → `engine.renderFrame`。
- **产出**：渲染出的第一帧"三个色块 + 一行字"，以及 `prng` 的可复现性测试。
- **验收**：同一 `t` 渲两次逐字节相同（或差异 ≤ 1/255 且只出现在 GPU pass 上）；换种子画面明显不同；缺字时构建失败。
- **谁**：全 DS。人只做一件事：**打开预览看一眼**（是否上下颠倒、字体是否加载、颜色是否对）。

### 第 5 步：把检查脚本做齐（DS，1 个对话）

- **输入**：`check_flash.py` / `check_sync.py` / `luma.py` / `compare_sheets.py` / `storyboard.mjs` 的判据（第 5 节）。
- **动作**：实现 + 用**故意做坏的样本**验证它们真的会失败（造一个 4 次/秒闪的片段，看是否 FAIL；造一个音频延迟 100 ms 的片段，看是否报 +100 ms）。
- **产出**：5 个可运行的检查 + 一份「它们各自的已知盲区」。
- **验收**：坏样本必须被抓到。**没抓到的检查等于没有检查。**
- **谁**：DS 写；**人做坏样本**（人知道怎么坏）。

### 第 6 步：先做最短的一段（DS + 人看，半天）

- **输入**：第 3 步里挑一段 8–16 秒、只有界面 + 1 张版画。
- **动作**：按 T2 写镜头；出 `--sheet` 图；人看完提一次修改；跑 4 类结构检查 + 缩图比对。
- **产出**：一段能看的片子 + 一份"流水线是否顺手"的结论（出图快不快、改动是否只涉及一个文件）。
- **验收**：storyboard 通过；比对报告零无关差异；人看完只说得出"内容"层面的意见，说不出"工程"层面的意见。
- **谁**：DS 实现，**人必须看**（这一段的目的是把头 5 步的假设一次性打穿）。

### 第 7 步：批量做其余段落（DS 主力 + 人逐段验收）

- **输入**：第 3 步的规格表。
- **动作**：一段一对话。**顺序按"最便宜 → 最重要 → 最贵"**：先做能立刻验证工程的段（如 A-1），再做全片最重要的一段（第四版是 H 段的最后一帧静帧），最后做依赖最多的段。
- **产出**：每段一个文件（`src/scenes/NN_name.js`），每段一版 `--sheet` 图。
- **验收**：每段做完立刻跑：storyboard（4 类）、`luma.py`（亮度形状）、缩图比对（是否碰坏别人）。**「Do it when the section is done, not at the end.」**
- **谁**：DS 实现；人负责三件事——**看得出不对**（首帧轮廓、版画像不像 emoji、脸有没有被扭曲）、**听得出不对**（踩点）、**取舍**（这一段是不是该删）。

### 第 8 步：逐段测闪光与同步（脚本 + 人判）

- **输入**：每段导出的 1080p60 片段。
- **动作**：`export.mjs --start X --end Y --width 1920 --height 1080 --fps 60 --out out/chk_x.mp4`，再跑 `check_flash.py`；关键段跑 `check_sync.py`。
- **产出**：每段一行数字：一般闪烁最差一秒 / 红闪 / 单帧突跳 / 提示点滞后。
- **验收**：闪烁 ≤ 3、红闪 0、无单帧突跳、提示点 |差| < 34 ms（半帧）。**不过就不许往下做**——留到最后，改动成本会翻十倍。
- **谁**：脚本判；人只在 FAIL 时决定"删动作 / 降强度 / 改阶梯式"。

### 第 9 步：全片合成与结构性体检（脚本，1 小时）

- **输入**：全部段落。
- **动作**：`npm run storyboard`（全覆盖 / 全对拍 / 全 moment / 无 fallback）、全片导出 1080p60、`npm run check`。
- **产出**：`STORYBOARD.md`、全片预览、`out/check_flash_preview.txt` / `check_sync_preview.txt` / `luma_preview.txt`。
- **验收**：`STORYBOARD.md` 的「检查」四行全绿；三个 txt 里的数字抄进 README 的「目前状态」。
- **谁**：全脚本。人只看四行结论。

### 第 10 步：看片、只改"必须改"的（人 + DS，1–2 个对话）

- **输入**：全片预览。
- **动作**：完整看 2 遍（一遍听，一遍看）。写成 T3 格式：**现象 + 测量 + 新时间表 + 不该动的清单**。一轮只改 2–3 件事。
- **产出**：修复轮提示词 + 改后的检查片段。
- **验收**：除了点名的时间窗，其余段落 `compare_sheets.py` 零差异。**这条比"看起来更好"更重要**——它保证修复没有伤到已经通过的部分。
- **谁**：**人看、人写修复单**；DS 改。

### 第 11 步：4K（脚本，几小时到一夜）

- **输入**：通过 1080p 检查的工程。
- **动作**：`export:4k`（`h264_nvenc`，不可用回退 `libx264 -preset slow -crf 16`，`aac 320k`），4K 下重跑 `check_flash.py`。
- **产出**：4K60 成片 + 单帧 4K 抽帧（特写边缘、最后一帧）。
- **验收**：4K 下的闪烁与同步同样通过；特写按原尺寸看没有锯齿/糊边（`f_eye`、`f_reach` 这类放大 > 1.75× 的必须是矢量路径）。
- **谁**：脚本；人只看 4K 抽帧的边缘。

### 第 12 步：发布前检查与交付（人和脚本各一半）

- **输入**：4K 成片、检查数字、素材授权。
- **动作**：`npm run check:lyrics`（入库不得有歌词/音频）；README 写清「成片时间 = 歌曲时间 + 5 秒」、闪光范围由脚本盖章；CREDITS 写授权（剪影 CC BY-NC-SA、字体 OFL、AI 生成声明、非官方同人声明）；导出说明写「哪里没照规格做、原因」。
- **产出**：可发布的文件 + 可复现的命令 + 一份诚实的差异报告。
- **验收**：任何人拿到仓库 + 自己的歌，能按 README 从零导出一支同规格的片子。
- **谁**：脚本保证「不含歌词」；**人写授权与声明**（这属于法律责任，不交给模型）。

## 8. 精致度硬规则清单（32 条，可勾选）

复制到你的 `docs/CHECKLIST.md`，逐条打勾。**只要有一条打不上，就先别导出。**

### A. 时间（5 条）

- [ ] **A1** 每帧只由 `renderFrame(t)` 决定：没有跨帧状态、没有 `Math.random()`、没有 `Date`。
- [ ] **A2** 所有剪辑点只用 `B()`/`Bt()`/`H()`，代码里搜不到裸数字时间。
- [ ] **A3** 不在网格也不在行首的时间，全部集中在 `cues.js` 一个文件，且每项标了来源（measured/audit/initial/ear）。
- [ ] **A4** 片头 preroll 在负时间，成片时间 = 歌曲时间 + preroll，导出档写了 `mv_start` 标签。
- [ ] **A5** 同一 `t` 渲两次一致（GPU 例外已记录在案）。

### B. 结构（5 条）

- [ ] **B1** `storyboard` 四行全绿：歌词全覆盖 / 切点全在半拍网格 / 每镜有 moment / 无 todo 后备镜头。
- [ ] **B2** 任意时刻最多两个镜头活着，转场重叠区被钳制过（没有镜头被吃掉）。
- [ ] **B3** 每个镜头的 `moment` 回答"这是哪个时刻"，版画回答"哪个词、由什么结束"。
- [ ] **B4** 每个 `layout` 以 `interface:` / `PLATE:` / `CODE:` 开头（画面种类可统计）。
- [ ] **B5** 有 fallback 机制，且交付时 fallback 数量为 0。

### C. 颜色与字体（6 条）

- [ ] **C1** 颜色只有状态、没有色值散落在代码里：搜 `#` 只出现在 `config.json`。
- [ ] **C2** 语义固定：橙=我、米白=你、红=错误、灰=缺席；全片没有第二套语义。
- [ ] **C3** 颜色只在事件发生时改变；每个状态变化能指到那一帧的叙事事件。
- [ ] **C4** 「红第一次出现」这类规则有明确时间点，且能被脚本查（例：129.34 s 前无 `err`）。
- [ ] **C5** 字体三分工：等宽=系统/代码、衬线=说的话/歌词、无衬线=界面/使用者；没有第四种。
- [ ] **C6** 字体与图片在第一帧前全部加载完；缺字会让构建失败而不是静默降级。

### D. 画面（7 条）

- [ ] **D1** 每个镜头至少三层：底（永远不是纯黑）/ 主体 / 前景或界面。
- [ ] **D2** 版画只用三墨（+ 允许的专色）；明暗来自第二墨或错位阴影版，没有渐变。
- [ ] **D3** 版画第一帧就是干净、一眼认得出的整体轮廓；缩到 640 宽仍认得出。
- [ ] **D4** 每张具象图单独渲 1920×1080 无歌词看一遍：不看字能说出是什么。
- [ ] **D5** 界面上没有调试 HUD、没有占位文字、没有重复的歌词。
- [ ] **D6** 画面上的每个词要么是歌词，要么是为这一刻写的简短原创文案。
- [ ] **D7** 有脸的镜头不扭曲、不动嘴、不用代码画脸、不撕裂；黑墨背后垫了纸底/光晕/描线。

### E. 运动与转场（4 条）

- [ ] **E1** 每个转场都有动机（歌词/叙事），不是装饰；类型从固定表里选，不即兴发明。
- [ ] **E2** 运动有缓动、错峰、次级运动；没有"只靠透明度淡入"的镜头。
- [ ] **E3** 有脸的画面只用 cut/fade/错版/降帧；撕裂只出现在无脸版画与色带上。
- [ ] **E4** 快动作有运动模糊或阶梯式推进；没有"穿过条纹/方块墙"的运动闪光。

### F. 检查（4 条）

- [ ] **F1** `check_flash`：任何 1 秒窗口 ≤ 3 次（一般与红色两种），单帧突跳 0。
- [ ] **F2** `check_sync`：音频偏移 |Δ| < 半帧；提示点 |Δ| < 半帧；关键词行 ±60 ms 内占比接近 100%。
- [ ] **F3** `luma`：全片最亮帧是结尾那一帧（或明确的爆点）；同一镜头内亮度回落 0 条。
- [ ] **F4** `compare_sheets`：改动只影响点名的时间窗，其余零差异（已知例外已登记）。

### G. 交付（1 条）

- [ ] **G1** 任何人用仓库 + 自己的歌，能按 README 从零导出同规格成片；`check:lyrics` 通过；授权与 AI 生成声明齐全。

## 附录 C：术语对照（读源码时会遇到）

| 词 | 含义 |
| --- | --- |
| 分版 / 三墨 | 把一张图按墨色拆成橙/米白/黑三张蒙版 |
| 套印 / 套准 | 三张蒙版对齐 |
| 错版 | 故意套不准（10/18/28 px），用它做「腐坏」 |
| 撕裂 | `glitch` 转场与 `fx.glitch`；图案必须保持 ≥ 6 帧 |
| 闪入 | 图形在 1–2 帧内整体出现，不带白场 |
| 棘轮（ratchet） | 镜头内亮度只升不降，降只发生在切点 |
| fallback / 后备镜头 | 某段还没做时，把歌词当消息逐行打出的占位镜头 |
| preroll | 歌曲开始之前的无声警告页，占用负时间 |
| 状态（state） | 调色盘的一个命名状态，不是一种「风格」 |
| moment | 镜头的一句话说明：这是叙事里的哪个时刻 |
