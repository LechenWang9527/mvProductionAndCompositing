# 人声与字幕逐句对齐核查

核查日期：2026-11-11。只读检查；未试听、未运行语音识别/对齐任务、未改动音频或时间轴。本报告不把混音 RMS、ASR 锚点相似度或字符插值称为人声实测。

## 已证实

- `analysis/align_lyrics2.py` 的用法是 `python align_lyrics2.py <asr.lrc> <lyrics.txt> <duration> <out.json>`；脚本把 ASR LRC 每个块的字符在当前/下一块时间之间线性分配，再用 `SequenceMatcher` 对齐歌词。未命中的字符由 `fill_gaps` 插值，行尾统一设为末字符时间 `+0.6s`。`analysis/align2.log` 记录输出为 `lyrics/og_timing.json`、ASR 共 1106 字/23 段；19 个锚点相似度均为 1.00，但这不是人声置信度。日志未保存输入文件的完整命令行。
- `The OGs 自动识别.lrc` 与 `.srt` 均有 81 条 ASR 块，起始时间最多相差 0.001 秒，不能视为两份独立的人声校验。LRC 首条为 14.990 秒，末条为 300.060 秒。ASR 把定版词“硫化的苦我吃过”识为“路滑的苦我吃过”，片尾把“未来有我留的灯”识为“未来有我留着的”。
- 歌曲时间基准吻合：`analysis/og_22050.wav` 为 22050 Hz 单声道，ffprobe 时长 305.876463 秒，四舍五入为 JSON 的 305.88 秒；MP3 容器报告 305.920 秒。后续人工标注应以 WAV 的时间轴为准，避免 MP3 时长差异引入偏移。
- 新脚本检查了 167 行：`og_timing.json` 的 section/text 与 `og_lyrics.txt` 逐行完全一致，字符数组也与每行可见字符一致。负起点、非正行时长、起点/字符顺序回退均为 0。
- 当前 `end` 字段不是实测唱词结束点：167 行都约等于末字符时间 `+0.6s`。因此有 166 组相邻行的存储区间表面重叠，不能据此判断人声重叠或字幕空白。行与行的字符起点间隔没有超过 0.8 秒的异常；片尾最后一句内部则有 0.831、0.832、0.831、0.832、1.663 秒间隔。最后一行存储 `end=305.899`，比声明时长多 0.019 秒；这是需听校的边界，不是已证实的声乐错位。
- 最低分段字符命中率为 `19 allen` 的 6/37（16.2%），其次是 `15 wuhan` 的 11/32（34.4%）。缺失字符会被插值补齐，故相关行应优先核对。最长歌词行按可见字符计为“工艺的未来都是 Punchline”（16 字），候选范围 269.867–274.655 秒。

## 本机工具与模型缓存

- 可用 ACE Studio CLI 0.18.7（对应 ACE Studio 2.1.9）。其本机帮助列出中文 `generative vocal-to-midi`，但该命令接收音频并向 Sing 轨写入识别音符/歌词，不接收定版歌词作 forced alignment；`lyric fill` 是把文字分配给已有音符。只查阅了帮助，没有启动会改工程的任务。
- 已查的项目 Python 环境中，`_trials/venv_torch` 有 torch、torchaudio、transformers；`_trials/venv_librosa` 有 librosa、soundfile；`_trials/venv_audio2` 未发现这些语音/对齐包。三个环境均未发现 WhisperX、faster-whisper、stable-whisper、aeneas、CTC forced aligner、Vosk 或 Praat。
- 用户级 Hugging Face 缓存有 `faster-whisper-large-v3-turbo` 与 `faster-whisper-medium` 权重；检查到的缓存没有 wav2vec2/CTC forced-alignment 模型。Whisper 权重用于 ASR，不能单独提供与指定歌词的 forced alignment。项目中可用 torch 环境也没有相应的识别/对齐包。
- PATH 中没有 ffmpeg、WhisperX、MFA、Audacity、Praat 等命令；仓库现有 `_trials/ffprobe_app` 含 ffprobe，可只读查看媒体元数据。只在几个项目虚拟环境和已知模型缓存中检查，未扫描整盘。目前可见的歌曲相关文件里未发现明确标为分离人声的 stem；歌曲源是 MP3 与其 WAV 派生文件。

## 最小成本逐句听校

1. 以 `analysis/og_22050.wav` 为参考，在 ACE Studio 临时工程/副本中作为普通音频轨播放，按 `priority_10.csv` 的候选点前后各约 1 秒循环；用时间尺读播放头，不运行 Vocal-to-MIDI/歌词填充，也不保存到制作工程。记录第一音节可听到的辅音/元音起点；候选 start/end 只作定位窗口，不作实测值。没有独立人声轨时直接听全混音，RMS/鼓点不代替人声起点。
2. 在模板填 `human_vocal_onset_s`、`delta_s = candidate/current start - human onset`、复核人和备注。先核对四次相同副歌，再听变体、低命中段、最长行与片尾。若一句无误，再对需要逐字高亮的行单独标每字/音节起点；不要把 ASR 字符均分时间当逐字实测。
3. 仅在听校表留下证据后再修对应歌词时间；音频文件保持不动。当前没有可直接执行的中文 forced aligner。若以后选用 ACE Vocal-to-MIDI，它只能作为另一次转录参考，不能当定版歌词的对齐结果。

## 改动后防漂移

- 保留已填写的 `manual_onset_template.csv`，以 `id`（段名、行号与文本）匹配，不按可能变化的行号单独匹配。新时间轴用 `node analysis/audit_lyric_timing.mjs` 重算结构核查；该脚本只在模板不存在时创建模板，不覆盖已有听校记录。
- 每条已核对行计算 `edited start - human_vocal_onset_s`。未授权/未听校的起点变化若超过 0.001 秒即标记为漂移；允许的字幕修正应满足人工起点偏差绝对值不超过 0.10 秒，超出则重听。改动后复核文本/字符仍匹配、起点单调、无负时长，并确认除已知片尾 `+0.019s` 外没有新越界；本核查不自动改写这项既有边界。
- 若只改布局/镜头，应不触碰歌词时间文件；导出后抽查这 10 个候选，确认同一歌曲时钟下字幕显示点与听校表一致。
